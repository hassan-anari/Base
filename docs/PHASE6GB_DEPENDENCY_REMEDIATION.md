## Tokio compatibility and patch review

The canonical [advisory](https://rustsec.org/advisories/RUSTSEC-2026-0386) names
1.51.6/1.53.3 as patched lines. Registry metadata confirms 1.53.3 is not yanked
and declares Rust 1.71, compatible with the existing toolchain. The published
1.53.3 changelog/source includes upstream #8587: explicit unsafe
`AsyncFd::register`/`register_with_interest` contracts and deprecation of the old
unsound safe constructors. This does **not** mean every historical API is removed.
The application does not call them and adds no unsafe adaptation. All-target
compilation and Clippy check the actual enabled transport/runtime call sites.

The reviewed 1.48–1.53 runtime changes include scheduling, timers, channels,
semaphore/waker handling and socket/platform fixes. Full protocol, mTLS, restart,
nonce/recovery and real validator gates must validate the resulting behavior;
compilation alone is not acceptance. Existing `full` features stay enabled;
no `tokio_unstable` features, new runtime flags or timeout relaxations are added.
Required tokio-macros 2.7.2 uses syn 3.0.6, already present in the original lock;
no new syn version is introduced. Existing mio/socket2 pins already satisfy the
new Tokio ranges and remain unchanged.

Lock resolution changes only the Tokio/macros versions. It removes unused
Tokio-owned backtrace/io-uring/platform dependencies as well as scc/sdd, reducing
the lockfile from 255 to **244 packages**. CGGMP24/keygen/key-share/hd-wallet,
FROST, curve libraries, ring, rustls, certificate verification and persistence
serialization versions stay pinned. The lockfile is generated by Cargo, not
edited to hide advisory entries.

## Removing scc without changing TON authorization semantics

The [scc advisory](https://rustsec.org/advisories/RUSTSEC-2026-0205) is fixed only
in >=3.8.4. everscale-types 0.1.2 requires scc `^2.1` for its optional sync
feature, so forcing scc 3.x is not a compatible dependency update. The registry's
latest everscale-types release is still 0.1.2. We instead remove the unused
thread-shared-cell capability and its dependency using the upstream-supported
feature configuration, without editing/vendoring cell algorithms.

The sole application import of everscale-types is `protocol/src/ton.rs`.
`code`, `init`, `comment`, `jetton_address` and `TonAuthorization::signing_hash`
create their cells on each synchronous call and return owned strings/bytes.
Cells are never stored globally, serialized into request models, returned to
async callers, held across await or shared with other threads. The upstream
non-sync branch uses Rc/Weak and, for optional UsageTree tracking, RefCell over
ahash::HashSet; the sync branch used Arc and scc::HashSet. Our verifier does not
use UsageTree. Rust's Send/type checking rejects any accidental transfer of
these Rc cells into multithreaded async state; no unsafe Send/Sync bridge exists.
Independent requests continue to run on different threads with separate cells.

This preserves the existing upstream BOC parsing, cell hashing, fixed contract
artifacts, hash/address reconstruction and exact signed-message comparison.
No TON network, shard, asset, wallet-version or production policy is extended.
The genuine TON/native/token, FROST and integrated gates remain mandatory,
including negative authorization mutations and independent serializer/hash checks.
`cargo tree --locked --target all` and the generated lockfile establish complete
removal of scc/sdd for the resolved feature graph; no advisory is reclassified
as harmless to obtain that result.

## Atomic-polyfill: decisive incompatibility and required independent assessment

The [maintenance advisory](https://rustsec.org/advisories/RUSTSEC-2023-0089)
lists portable-atomic as an alternative, with **no patched atomic-polyfill
release**. The latest published compatible releases inspected in the registry
are frost-core 3.0.0 and Postcard 1.1.3. frost-core's serialization feature
enables Postcard `^1.0.0` with `alloc` and defaults enabled. Postcard's default
`heapless-cas` feature enables Heapless `^0.7.0` and its `cas` feature.
Heapless 0.7.17 brings the archived atomic-polyfill on certain embedded targets.
Heapless 0.8.0/0.9.1 use maintained portable-atomic, but they are outside the
published Postcard dependency's compatible range.

Actual resolution attempt, against the changed workspace:

```text
cargo update --manifest-path mpc-side/Cargo.toml -p heapless --precise 0.8.0
error: failed to select a version for the requirement `heapless = "^0.7.0"`
candidate versions found which didn't match: 0.8.0
required by package `postcard v1.1.3`
... required by `frost-core v3.0.0` / `frost-ed25519 =3.0.0`
```

The resolver exits 101 without changing the lockfile. Adding a newer Heapless
as a separate direct dependency would retain the affected old instance. Renaming
portable-atomic as atomic-polyfill would not satisfy the dependent package
identity/version and target/critical-section contracts. Disabling defaults on
a downstream direct Postcard declaration cannot subtract the features enabled
by frost-core: Cargo features are additive. Removing FROST serialization would
break the existing persisted share/commitment/signature encoding and recovery
contracts; it is not a safe remediation.

`cargo tree --locked -i atomic-polyfill` on the actual Linux x86_64 service
target has no selected dependency; `--target all` retains the path above.
Heapless 0.7.17's manifest/build script select the polyfill for AVR,
riscv32i/riscv32imc bare metal, thumbv6m and xtensa-esp32s2 targets. This verifies
the current host-build distinction, **not** safety on every platform, a waiver
of an unmaintained package or a guarantee against future target/feature changes.
The audit still reports the package because it is in the full lockfile.

**Independent risk assessment required:** confirm the supported deployment-target
boundary and maintenance exposure; review either an upstream frost-core change
to disable unused Postcard defaults while retaining `alloc`, or a maintained
Postcard/Heapless migration. Any source patch/fork must be explicitly owned and
reviewed, including portable-atomic target/critical-section guarantees if used.
Before acceptance, compare serialized FROST shares, public key packages,
commitments/signatures and persisted nonce/execution recovery byte for byte;
rerun genuine all-pair FROST DKG/signing, crash/restart and Solana/TON validators.
This pass does not introduce an unreviewed FROST source fork to make audit quiet.
**Disposition remains BLOCKED, not remediated or implicitly accepted.**
